# 類似判定の結果を保存して使い回す（Issue #21）設計

2026-11-21

## 目的

類似画像の確認では、判定のたびに全画像をデコードして dHash・解像度・サイズを求めている。時間の大半はデコードで、SMB 上のフォルダでは特に重い。今は結果をメモリ上だけに持つので、アプリを再起動するたび、仕分け元を読み直すたびに全画像を読み直している。

一度判定した画像は、再起動後も保存した結果を読み出すだけにして、2 回目以降の判定をすぐ終わらせる。

## 決定事項（ユーザー確認済み）

- 判定結果を**ディスクに保存し、再起動後も使う**（何回でも使い回せるように）
- 使い回す範囲は **B 案**: 同じ場所のまま変わっていない画像に加えて、**Lumiwake が振り分け・削除フォルダへ移動した画像も、移動先で記録を引き継ぐ**
  - 他のアプリやエクスプローラーで移動・リネームされた画像は当てない（別の画像として判定し直す）
- 保存方式は**アプリのキャッシュフォルダに 1 ファイル**（JSON）。SQLite（配布物が増える）と仕分け元フォルダ内への保存（SMB・写真フォルダを汚す、読み取り専用の共有で使えない）は採らない

## 目標と範囲外

- 目標: 2 回目以降の判定で、変わっていない画像はデコードしない。誤った結果は使わない（古い記録で違う画像を「似ている」と出さない）
- 範囲外:
  - 「中身が完全に同じか」の読み比べ結果（`SimilarScan::exact`）の保存。サイズが同じ組にしか走らず、今回は対象にしない
  - 読めなかった画像（`table` の `None`）の保存。一時的に読めなかっただけかもしれないので、毎回読み直す
  - 記録を消すボタンなどの画面。記録は更新日時・サイズで確かめてから使うので、古い記録が残っても誤りにはならない。消したい場合はファイルを削除すればよい（説明ページに場所を書く）
- 失敗とみなすこと（動いていても）: 保存ファイルの読み書きの失敗で判定や仕分けが止まる、起動が遅くなる、壊れた保存ファイルで判定結果がおかしくなる

## 方式（Approaches）

| 案 | 内容 | 採否 |
| --- | --- | --- |
| 1. キャッシュフォルダに 1 ファイル | 起動後に初めて判定するときに全部読み、まとめて書き出す。依存は増えない（`serde_json` は導入済み） | **採用**。1 件 100〜150 バイト程度で、1 万枚でも 1〜2 MB。想定規模（1 回数百枚）なら全体の書き直しで十分速い |
| 2. SQLite | 1 件ずつ追記でき、件数が増えても速い | 不採用。C ライブラリの同梱で配布物が 1〜2 MB 増え、Windows のビルド手順も増える（軽量性の要件に反する） |
| 3. 仕分け元フォルダ内の隠しファイル | フォルダごと持ち運べる | 不採用。SMB 共有や写真フォルダにアプリのファイルを書くことになり、読み取り専用の共有では保存できない |

## 記録の中身と照合

- 1 件 = 画像ファイルの**今ある場所の絶対パス**、**更新日時**、**ファイルサイズ**、判定結果（dHash・幅・高さ）、**最後に使った日時**
- 使うのは、パス・更新日時・サイズの 3 つがすべて今のファイルと一致したときだけ。どれかが違えば読み直して記録を置き換える
  - 今のファイルの更新日時・サイズは、判定の各ワーカーが画像ごとに `metadata` で取る（今も `fingerprint` がサイズを取るために呼んでいる。追加の読み込みはない）
  - 更新日時はナノ秒まで比べる。精度の粗いファイルシステムでも、同じファイルなら毎回同じ値になるので問題ない
- 保存ファイルには形式のバージョンを持つ。ハッシュの計算方法を変えたらバージョンを上げ、古い記録は全部捨てる（違う計算方法の値を比べない）
- パスを UTF-8 で表せない画像は保存しない（毎回判定する）

## 移動した画像（B 案）

- Lumiwake の移動は、別ドライブでも更新日時を引き継ぎ（`fileops::fs` の `set_modified`）、サイズも変わらない。このため、移動元の記録を**移動先のパスで複製**すれば、移動先でもそのまま照合に通る
  - 更新日時を引き継げない環境では照合に通らず、読み直すだけ（誤った結果は使わない）
- 対象: 現在と切り替え前（`retired`）のセッションで、状態が `Moved { to }` または `Trashed { to, .. }` の画像。元の場所の記録（このセッションで判定したもの、または前回までに保存したもの）があれば、`to` の記録として複製する
- 移動元の記録は消さない（取り消しで戻ったときにそのまま使える。使われなければ下の掃除で消える）
- 複製するタイミング: 保存ファイルを書き出すとき（下記）。終了時にも書き出すので、その回に判定を開いていなくても、移動した画像の記録は引き継がれる

## 読み込み・書き出し

- 保存場所: `app_cache_dir()/similar-cache.json`（Linux は `~/.cache/<identifier>/`、Windows は `%LOCALAPPDATA%\<identifier>\`）。`AppState::new` にパスを渡す
- 読み込み: 起動時には読まない（起動を遅くしない）。最初に判定を始めたとき（`start_similar_scan`）、または終了時の書き出しで必要になったときに 1 回だけ読む
  - ファイルがない、壊れている、バージョンが違う: 空として扱い、エラーにしない（次の書き出しで作り直す）
- 書き出し:
  - 判定が終わったとき（待ちがなくなったとき）
  - 判定の途中でも、新しく判定した結果が一定件数（目安 200 件）たまるごと（異常終了しても大半が残るように）
  - アプリの終了時（`exit_app`。移動した画像の記録の複製もここで反映する）
  - アップデート後の再起動の前（`relaunch` は `exit_app` を通らないので、`updater.ts` から書き出しのコマンドを呼んでから再起動する）
  - 変更がなければ書かない
  - 一時ファイルに書いてから置き換える（途中で落ちても壊れたファイルを残さない）
  - 書き出しに失敗しても判定・終了は止めない（ログに残すだけ）
- 書き出しはロックを持ったまま行わない（判定のワーカーを止めない）。内容を写してから書く

## 掃除

- 書き出すときに、最後に使ってから **90 日**たった記録を捨てる
- 件数が上限（**20 万件**、20〜30 MB 程度）を超えたら、最後に使った日時の古いものから捨てる
- 「使った」とは、照合に通って結果を使ったとき、新しく判定したとき、移動先へ複製したとき

## 今のメモリ上の仕組みとの関係

- `SimilarScan` の `table`（元の場所のパスをキーにした、このセッションの結果）はそのまま残す。保存した記録は、その手前で「デコードせずに結果を得る」ために使う
- 仕分け元を読み直したとき（`reset`）に捨てるのは `table` だけで、保存した記録（とそのメモリ上の写し）は捨てない
- 判定の進み具合（`ScanStatus`）は今と同じ。記録から読み出した画像も「判定を終えた枚数」に数える（すぐ数が進む）

## テスト（先に書く）

- 記録の照合: パス・更新日時・サイズが一致すれば使い、どれかが違えば使わない
- 保存ファイル: 書いて読み直せる。壊れたファイル・バージョン違い・ファイルなしは空として扱う。書き出しは一時ファイルを経由する
- 掃除: 90 日使っていない記録を捨てる。上限を超えたら古いものから捨てる
- 判定: 保存した記録がある画像はデコードしない（デコードの呼び出し回数で確かめる）。更新された画像は読み直す。読み直した結果で記録を置き換える
- 移動: 振り分けた画像の記録が移動先のパスで残り、移動先を仕分け元として読み込んだときにデコードしない。移動元の記録も残る
- 再起動をまたぐ: `AppState` を作り直しても（同じ保存場所）記録を使う
- 失敗: 保存先に書けなくても判定は終わる
- テストの画像と保存先は一時ディレクトリだけを使う

## ドキュメント

- 説明ページ（日英）の類似画像の説明に、判定結果を保存して次回から速くなること、保存場所、消してよいことを書く
- `docs/handoff-notes.md` の類似画像の項と残課題（#21）を更新する
- `CLAUDE.md` のディレクトリ構成の `similar/` の説明に保存を加える

## 設計時の判断（ユーザー未確認。読みながら確認してほしい点）

- 終了時に加えて、アップデート後の再起動の前にも書き出す（上記）
- 同じ画像でもパスの書き方が違う場合（マップしたドライブ `Z:\` と `\\server\share`、シンボリックリンク経由など）は別の画像として扱い、判定し直す。パスの正規化はしない（SMB 上で解決するのに時間がかかるため）
- アプリを 2 つ同時に起動した場合は、後に書き出したほうの内容が残る。片方の記録が失われても、判定し直すだけで誤りにはならない
- 掃除の基準（90 日・20 万件）と、途中で書き出す間隔（200 件前後）

## 実装者に任せること

- 保存処理を置くモジュール（`similar/` の中に新しいファイルを作る想定）と型の名前
- 途中で書き出す件数の正確な値（200 件前後）
- JSON の具体的な形（形式のバージョンを持つこと以外）
- 更新日時の持ち方（UNIX エポックからのナノ秒など）
